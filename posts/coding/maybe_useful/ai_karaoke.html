老实打 K 轴，很枯燥吧

Wanakachi原创2026/10/25大约 12 分钟TechnologyPythonKaraoke

做过日文歌卡拉 OK 字幕（也就是常说的“打 K 轴”）的朋友都知道，这是一项多么折磨人的体力活——你得对着音频波形逐字敲时间轴，手动给生僻汉字标假名（Ruby），还得算好上下两行字幕的交替时机。常常一首四分钟的歌能打一个下午😃。

自己打工不如使唤 AI。既然现在语音识别和声学模型这么成熟，能不能把音频和现成的 LRC 歌词丢给 AI，让它直接吐出一份带逐字填色动画和日文注音的 ASS 字幕呢？

听起来像是把歌词喂给模型就能一键搞定的事，但真正动手写起来才发现，坑根本不在“模型准不准”上：伴奏会严重干扰时间轴定位，网上的 LRC 歌词里混着中文翻译和作词人信息，日语汉字在歌里的实际唱法经常和词典默认读音对不上（比如把“未来”唱成“きょう”），最后还得把时间轴、假名注音和 ASS 复杂的 \kf 动画标签严丝合缝地对齐。

于是，在经过和 AI 的激烈搏斗之后， 这个全自动卡拉 OK 字幕生成项目：AI_karaoke_subtitles 应运而生。从 4 月跑通初版、5 月加上 Web GUI，再到 9~10 月对底层对齐流程做彻底重构，它终于从一个“能跑的脚本”演进成了经得起真实歌曲考验的字幕流水线。

项目的核心处理链可以概括为五步：

  1. 输入：音频 + LRC

  2. 人声分离：使用 Mel-Band RoFormer / Demucs（支持伴奏相消）。

  3. LRC 清洗：剥离翻译与元数据、提取括号显式注音。

  4. 声学对齐：使用 MMS Karaoke CTC 强制对齐 + 冲突窗口恢复。

  5. 读音决策：优先级：LRC 显式 > Whisper 审计 > CTC 候选 > 词典默认。

  6. ASS 渲染：实现 Ruby 假名注音 + K1/K2 上下双行交替动画。

初版：先把完整闭环跑通

万事开头难，第一步的目标很简单：不管边缘情况有多脏，先把“音频 + LRC → ASS 字幕”这条链路打通。

初版我用了 Demucs 做人声和伴奏分离（如果你手头刚好有纯伴奏文件，也支持直接通过波形相消拿到更干净的人声），再用 Whisper 按歌词行切片做逐词定位，最后参考 Ruby_Kara 的思路写了个 kara_style.py，把普通时间轴渲染成带注音和逐音节填色的 ASS 字幕。

链路是通了，但拿到真实歌曲里一跑，马上撞上了三个让人头疼的细节。

问题 1：LRC 时间戳把间奏也吞了

网上的 LRC 歌词，通常只有每一句的“开始时间”，没有真正的“结束时间”——很多制作者都是直接拿下一句的开始时间当成上一句的结束时间。如果原样照搬，遇到两句歌词中间隔了十几秒间奏的情况，上一句歌词就会在屏幕上尴尬地挂满整个间奏。

所以，LRC 的时间戳只能当成搜索提示，绝不能当成最终边界。真正的结束时间应该尽量采用模型对齐出的“最后一个词的结束时间”：

# 约束歌词行结束时间：取最后一个已对齐词的结束时间 + 小缓冲，且不超过原 LRC 边界
last_word_end = aligned_words[-1].end
line_end = min(lrc_next_start, last_word_end + buffer_sec)

问题 2：野生 LRC 里的牛鬼蛇神

初版上线后才深刻体会到野生 LRC 的复杂性：同一个时间戳下可能并排躺着日文原词和中文翻译；开头 00:00.000 塞着作词、作曲和上传者签名；歌词正文里还夹杂着 頬(ほほ) 这种自带括号的注音，甚至是整句英文和声。

如果一股脑全塞给声学模型，对齐结果当场就会崩坏。因此解析器不得不加上一整套清洗规则：

  • 靠语言特征和相邻时间标签把中文翻译筛出去；
  • 不能看到 00:00.000 就一刀切全删，免得把某些贴着第 0 秒起唱的真歌词误杀了；
  • 像 頬(ほほ) 这种括号注音，要把括号从显示正文里摘除，但把 ほほ 留下来直接作为最终的 Ruby 假名；
  • 遇到省略号 … 等标点时，解析阶段必须保留用于最终显示，但在送入模型前必须过滤掉不可对齐的空节点。

问题 3：K1/K2 双行交替的假间奏陷阱

卡拉 OK 字幕最经典的效果是上下两行（K1/K2）交替出现，方便演唱者提前看下一句。但什么时候该重置回上行 K1 呢？自然是遇到间奏、进入新段落的时候（由参数 kara-sep-threshold-ms 控制）。

最初我图省事，直接比较相邻两句的 start 间隔，结果频频误判。原因很简单：如果上一句是个拖长音，两句 start 离得很远，但中间其实根本没有间奏。正确的语义必须是比较 “上一句真正唱完的时间（end）”到“下一句开始时间（start）”的空白间隔：

# 只有句间真实留白超过阈值，才判定为新段落并重置回 K1 样式
gap_ms = (curr_line.start - prev_line.actual_end) * 1000
if gap_ms >= kara_sep_threshold_ms:
    current_style = "K1"
    display_start = curr_line.start - (kara_advance_ms / 1000.0)  # 仅段落首句提前显示
else:
    current_style = "K2" if current_style == "K1" else "K1"

这样一来，新段落固定从上行 K1 开始并提前显示，同段落内严格上下交替，状态机比单纯按行号奇偶取模稳健得多。

GUI 化：让流水线变成趁手工具

5 月份我发现，虽然命令行已经能跑通全流程，但每次都要敲一长串参数终归不太优雅。于是我在不破坏 CLI 批处理能力的前提下，用 Web 界面给它套了一层 GUI：选好歌曲、歌词和可选伴奏，调一下模型和卡拉 OK 参数，点下按钮就能在网页里实时看到五阶段进度反馈。

听起来只是加个前端壳子，结果在打包 Windows 一键安装版时，工程化上的幺蛾子比算法还多😰 ：

  1. 启动假死与白屏：直接在顶层 import torch 和 stable_whisper 会花掉好几秒甚至十几秒，如果启动脚本傻傻地固定等 2 秒就拉起浏览器，用户看到的永远是个连接失败的白屏。最后我把重依赖全部改成了延迟导入（Lazy Import），后端加上 /healthz 探活接口，启动脚本轮询确认服务就绪后再自动打开浏览器。
  2. 神秘的 WinError 2：子进程调用 demucs 或 FFmpeg 时，在用户的隔离环境里经常找不到可执行文件，报错却只有冷冰冰的一句 WinError 2。改成优先调用 python -m demucs.separate 并显式补全隔离环境的 PATH 后才彻底消停。
  3. “为什么我跑得这么慢？”：排查后发现，不少 Windows 用户默认装上了 CPU 版的 PyTorch。后来安装脚本加上了 NVIDIA GPU 自动检测，优先拉取 CUDA 版本，并在黑框启动时直接把 torch=... cuda_available=... 打印在最显眼的位置；顺手还把默认塞在用户目录 .cache 里的庞大模型缓存全迁到了项目安装目录内，卸载时直接删文件夹就能干干净净。

字幕流程大重构：跟真实歌曲死磕

如果只拿一两首节奏舒缓的标准日文歌测试，故事到这里就结束了。但当我在 9 月拿出一堆曲风各异的真实歌曲（尤其是快节奏电音、带大量重复洗脑句和复杂和声的 ACG 歌曲）去跑时，旧流程的短板暴露无遗。

为了把项目从“能生成文件”变成“可解释、可回归”，我对整个字幕引擎做了一次伤筋动骨的重构：不仅把扁平脚本拆成了职责分明的七层包结构（application / audio / lyrics / alignment / pronunciation / subtitles / interfaces），还彻底换掉了对齐底座。

为什么放弃 Qwen 行级对齐，转向 MMS CTC？

重构初期，我其实尝试过用 Qwen3-ForcedAligner-Ultra 做行级对齐。它可以直接吃汉字输入，听起来很美好，但在真实歌曲上却频繁吐出重叠时间戳、零时长 token 和极其不稳定的行内切分；哪怕先把歌词全转成假名再喂给它，不仅没能稳定解决问题，反而把原词形和显示文本的映射关系弄丢了。

最终，生产路径切换到了专门针对日语卡拉 OK 场景微调的 CTC 强制对齐模型：NextFire/mms-300m-ForcedAligner-karaoke-ja-Latn（人声分离也升级支持了效果更好的 Mel-Band RoFormer）。LRC 时间戳只负责划定搜索窗口，CTC 在人声声学特征（emission）上寻找最优的罗马音/假名路径，再精确映射回每个字符或拍节（mora）的起止时间。

读音决策：歌词汉字到底该怎么念？

日语歌里最让人抓狂的就是“字面写法”和“实际唱法”不一致：比如异体字 每日 词典可能不认，或者作词人故意把 未来 注音成 ｷｮｳ。

如果完全信词典（kanjiconv），注音就会错；如果完全信语音识别（Whisper），伴奏一吵它又会胡言乱语。为此，我设计了一套保守的读音四级决策机制：

1. LRC 显式注音（如 未来(ｷｮｳ)） ──> 绝对优先，直接采用并从正文剥离括号
2. Whisper 听觉审计            ──> 仅在该词行内唯一、置信度达标且整句不退化时覆盖
3. CTC 声学候选                ──> 声学路径得分明显更优时采用
4. kanjiconv 词典默认          ──> 兜底方案

为什么要加这么多限制？

举个真实案例：在歌曲《SWEET DROPS》里，歌词写的是异体字 每日，Whisper 清晰地听到了 まいにち，这时候用 Whisper 的结果去纠正词典就非常完美。

但如果一行歌词里同一个词重复出现了两次，或者遇到词典不认识的未知复合词，绝不能无脑做全局覆盖或按字数硬拆——一旦局部误判，就会把整句正常的注音全改坏。无法可靠映射时，宁可退回整词 Ruby 注音，也绝不强行拆出错误的假名对应关系。

除了汉字，歌词里的 1, 2, 3 这种数字也被纳入了 token 链路（支持 auto|ja|en 读法切换），让每个数字都能分到独立的 \kf 填色时长，再也不会一整串数字瞬间同时变色了。

两个最诡异的顽固 Bug

在拿真实曲库做回归测试时，我还逮到了两个极具代表性的底层 Bug：

1. 消失的省略号与空读音节点

在跑《鈴がなる日》这首歌时，遇到一句 君の…君のこんなにも，程序直接抛出了 Cannot romanize lyric unit '' 崩溃退出。

排查发现，第三方分词器在处理省略号 … 附近时，会莫名其妙拆出一个 {'orig': '', 'hira': ''} 的幽灵空节点，这个空节点一旦流入 CTC 罗马音转换器就会当场爆炸。

解决办法是在“显示文本”和“对齐文本”之间划清界限：进入 CTC 之前统一拦截并过滤掉所有空读音节点，但原原本本地把 … 保留在 ASS 渲染树里。修复后全曲 49 条歌词一次通过，问题行对齐在 211.56–215.74s，和原轴漂移只有区区 9 毫秒。

2. 引发 C++ 底层 std::vector max_size 崩溃的洗脑重复句

跑《侵略ノススメ☆》时更刺激，Python 直接报了底层 C++ 的 std::vector::_M_fill_insert / max_size 内存异常。

这首歌开头有大量密集的重复短句。旧版在做“时间轴重叠恢复”时，采用的是局部修补策略：发现第 2 句和第 3 句重叠了，就把窗口往后挤一挤；结果挤完又撞上了第 4 句……如此反复拉扯，最终算出了一个结束时间小于开始时间的反向音频窗口！

Python 对负数长度的数组切片毫不报错，静默返回了 0 帧音频；而底层 C++ 扩展拿到 0 帧后算出了负数尺寸，转成无符号整型瞬间变成天文数字，直接撑爆了 std::vector。

为了根治这个问题，我重写了冲突恢复算法——不再头疼医头，而是把所有互相挤压的歌词行按区间连通关系合并成一个“冲突连通组”，一次性扩展边界并联合重对齐：

# 连通冲突组扩窗重对齐 + CTC 最小帧数防御
for group in find_connected_overlap_groups(aligned_lines):
    window_start = max(0.0, group.min_start - pad_sec)
    window_end = min(audio_duration, group.max_end + pad_sec)
    audio_slice = vocal_audio[int(window_start * sr) : int(window_end * sr)]
    
    # 防御性检查：严禁过短或反向切片流入底层 C++
    if len(audio_slice) < MIN_CTC_AUDIO_FRAMES:
        mark_group_as_fallback(group, reason="insufficient_audio_frames")
        continue
    realign_group_jointly(group, audio_slice, window_start)

加上连通组联合重对齐与帧数守卫后重跑《侵略ノススメ☆》，82 条有效歌词全部丝滑落位，再也没有触发过一次底层异常。

验证与结语

重构到最后，项目的评判标准已经不再是“能不能吐出一个 .ass 文件”，而是诊断报告、ASS 字幕、假名读音和时间轴能不能彼此完全对上账。

为此，我把单元测试和边界回归从最初的 9 项一路补到了 69 项，加上 Ruff 静态检查与 Node 端的 ASS 预览测试，并用真实曲库在 本机 GPU 上跑完了全套端到端验证，总算是比较满意了。

回头看这半年多的折腾，最大的感触是：做 AI 应用工程，往往不是在拼谁换的模型更新，而是在围绕数据边界不断做“减法”——不把中文翻译送进日文 CTC，不把标点符号伪装成声学 token，不拿低置信度的识别结果强行覆盖词典，也不让非法的音频切片流入底层 C++。当解析器、声学模型和字幕渲染器共享同一套干净、可解释的中间表示时，那些藏在真实歌曲里的疑难杂症，才终于迎刃而解。
